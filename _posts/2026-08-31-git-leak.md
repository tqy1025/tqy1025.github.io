## 原理

Git 泄漏是指 `.git` 目录被意外暴露在生产环境中，攻击者可以通过访问 Git 元数据文件（如 `.git/HEAD`、`.git/config`、`.git/objects/*` 等）重建完整的源代码仓库。

`.git` 目录保存了 Git 仓库的版本管理信息，包括：

- 当前分支信息
- 提交记录
- 文件对象
- 历史版本
- 远程仓库配置
- 已经删除但仍存在于历史提交中的文件

常见结构如下：

```text
.git/
├── HEAD
├── config
├── index
├── refs/
│   ├── heads/
│   └── remotes/
├── logs/
└── objects/
    ├── info/
    ├── pack/
    └── xx/
```

其中：

- `.git/HEAD` 指向当前分支。
- `.git/index` 保存暂存区中的文件路径信息。
- `.git/refs` 保存分支和标签引用。
- `.git/logs` 可能泄漏提交记录和提交者信息。
- `.git/objects` 保存提交、目录树和文件内容。
- `.git/config` 可能泄漏远程仓库地址及内部配置信息。

## 检测方法

### 直接访问关键文件

可以检测以下路径：

```text
/.git/
/.git/HEAD
/.git/config
/.git/index
/.git/logs/HEAD
/.git/refs/heads/main
/.git/refs/heads/master
```

使用 `curl` 检查：

```bash
curl -i https://example.com/.git/HEAD
```

若响应正文包含：

```text
ref: refs/heads/main
```

或者：

```text
ref: refs/heads/master
```

说明 Git 元数据已经泄漏。

也可以检测配置文件：

```bash
curl -i https://example.com/.git/config
```

典型内容可能包含：

```ini
[core]
    repositoryformatversion = 0
    filemode = true
    bare = false
```

### 根据 HTTP 状态判断

常见响应状态：

| 状态 | 含义 |
|---|---|
| `200` | 文件可以直接读取，基本可以确认存在泄漏 |
| `301/302` | 发生跳转，需要跟随跳转继续判断 |
| `403` | 目录列表被禁止，但单个文件仍可能可以读取 |
| `404` | 当前路径没有公开，但仍需确认是否有路径重写或其他部署目录 |

`/.git/` 返回 `403` 并不代表安全，因为服务器可能只禁止目录列表，却仍然允许访问 `/.git/HEAD`、`.git/index` 和 `.git/objects/*`。

跟随跳转检测：

```bash
curl -iL https://example.com/.git/HEAD
```

只查看状态码：

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  https://example.com/.git/HEAD
```

### 检查响应内容

除了状态码，还应确认内容是否具有 Git 文件特征：

```bash
curl -s https://example.com/.git/HEAD
```

可能返回：

```text
ref: refs/heads/main
```

检查 `.git/config`：

```bash
curl -s https://example.com/.git/config
```

可能看到：

```ini
[remote "origin"]
    url = git@example.internal:team/project.git
```

远程地址可能进一步泄漏内部域名、用户名或项目名称。

## 利用工具（包括用法）

### git-dumper

`git-dumper` 可以从允许访问部分 `.git` 文件的网站中恢复 Git 仓库。

项目地址：[arthaud/git-dumper](https://github.com/arthaud/git-dumper)

安装：

```bash
python3 -m pip install git-dumper
```

基本用法：

```bash
git-dumper https://example.com/.git/ recovered-repository
```

进入恢复目录：

```bash
cd recovered-repository
```

查看状态：

```bash
git status
```

查看所有分支：

```bash
git branch -a
```

查看提交记录：

```bash
git log --all --oneline
```

查看某次提交：

```bash
git show <commit-id>
```

查看所有分支的改动记录：

```bash
git log --all -p
```

搜索历史提交中可能存在的敏感信息：

```bash
git log --all -p -- .env
git log --all -p -- config.php
git log --all -p -- application.yml
```

也可以搜索关键词：

```bash
git log --all -p | grep -Ei \
  "password|passwd|secret|token|api[_-]?key"
```

如果工作区没有自动恢复，可以尝试：

```bash
git reset --hard HEAD
```

或者：

```bash
git checkout -f
```

### GitTools

GitTools 包含用于检测、下载和提取 Git 仓库的脚本。

项目地址：[internetwache/GitTools](https://github.com/internetwache/GitTools)

下载工具：

```bash
git clone https://github.com/internetwache/GitTools.git
cd GitTools
```

使用 Dumper 下载泄漏的仓库：

```bash
bash Dumper/gitdumper.sh \
  https://example.com/.git/ \
  recovered-repository
```

使用 Extractor 提取各个提交中的文件：

```bash
bash Extractor/extractor.sh \
  recovered-repository \
  recovered-files
```

Extractor 会遍历可用的 Git 对象，并按照提交分别还原文件。输出目录可能类似：

```text
recovered-files/
├── 0-<commit-id>/
├── 1-<commit-id>/
└── 2-<commit-id>/
```

需要注意，这里的数字通常表示发现顺序，不一定是提交时间顺序。

### GitHack

GitHack 是较早期的 Git 泄漏恢复工具。

项目地址：[lijiejie/GitHack](https://github.com/lijiejie/GitHack)

下载：

```bash
git clone https://github.com/lijiejie/GitHack.git
cd GitHack
```

运行：

```bash
python GitHack.py https://example.com/.git/
```

部分旧版本可能依赖较早的 Python 环境。如果出现兼容问题，可以优先使用 `git-dumper`。

### 手工分析恢复后的仓库

恢复仓库后，首先查看提交记录：

```bash
git log --all --oneline --decorate
```

查看当前文件：

```bash
find . -type f \
  -not -path "./.git/*"
```

查看某次提交修改了哪些文件：

```bash
git show --stat <commit-id>
```

查看指定文件的历史：

```bash
git log --all -p -- path/to/file
```

列出某次提交的完整目录树：

```bash
git ls-tree -r --name-only <commit-id>
```

读取某次提交中的文件：

```bash
git show <commit-id>:path/to/file
```

例如：

```bash
git show a1b2c3d:index.html
```

如果敏感文件已经被删除，可以查找删除记录：

```bash
git log --all --diff-filter=D --summary
```

再从删除前的提交中读取：

```bash
git show <commit-id>^:path/to/deleted-file
```

## 防御措施

### 部署时排除 `.git`

不要直接把项目根目录完整复制到生产服务器。

错误示例：

```bash
cp -r project/ /var/www/html/
```

更安全的做法是只部署构建结果：

```bash
cp -r dist/ /var/www/html/
```

或者使用打包命令排除 `.git`：

```bash
rsync -av \
  --exclude=".git" \
  --exclude=".env" \
  project/ /var/www/html/
```

### Nginx 禁止访问

在 Nginx 配置中加入：

```nginx
location ~* /\.git(?:/|$) {
    return 404;
}
```

修改后检查配置：

```bash
nginx -t
```

重新加载：

```bash
sudo systemctl reload nginx
```

### Apache 禁止访问

可以在 Apache 配置中加入：

```apache
RedirectMatch 404 /\.git
```

或者：

```apache
<DirectoryMatch "/\.git">
    Require all denied
</DirectoryMatch>
```

重新加载 Apache：

```bash
sudo systemctl reload apache2
```

### 删除服务器上的 `.git`

如果生产目录不需要 Git，可以删除部署目录中的 `.git`：

```bash
rm -rf /var/www/html/.git
```

执行前必须确认目标路径准确，避免误删开发仓库。

只删除 `.git` 目录并不能消除已经发生的泄漏。如果仓库中出现过密码、令牌或密钥，还必须立即进行吊销和轮换。

### 使用 CI/CD 部署构建产物

推荐流程：

```text
代码仓库
   ↓
自动构建
   ↓
生成 dist、build 或 public
   ↓
仅将构建产物部署到服务器
```

生产环境不应包含：

```text
.git/
.github/
.env
tests/
开发脚本
本地配置
```

### 避免提交敏感信息

将敏感文件加入 `.gitignore`：

```gitignore
.env
.env.*
config.local.*
*.pem
*.key
secrets/
```

但需要注意，`.gitignore` 只对尚未被 Git 跟踪的文件有效。已经提交过的文件不会因为加入 `.gitignore` 而自动从历史记录中消失。

应该使用环境变量或专门的密钥管理服务保存：

- 数据库密码
- API Token
- SSH 私钥
- 云服务密钥
- JWT 签名密钥

### 泄漏后的应急处理

发现 Git 泄漏后，应当：

1. 立即阻止外部访问 `.git`。
2. 检查服务器访问日志，确定是否有人下载过相关文件。
3. 吊销并轮换仓库中出现过的密码、Token 和密钥。
4. 删除生产服务器上的 `.git` 目录。
5. 检查 Git 的全部历史提交，而不只是当前版本。
6. 必要时清理 Git 历史并重新发布仓库。
7. 检查泄漏的账号是否存在异常登录或权限滥用。
8. 修正部署流程，防止再次将版本库元数据上传。
